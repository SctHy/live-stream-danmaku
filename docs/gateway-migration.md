# 万人直播间的网关滚动下线

## 发布流程

网关收到 SIGTERM 或 SIGINT 后，立即让 `/readyz` 返回 503，并拒绝新 WebSocket 接入。与摘流同时到达的注册请求还会在房间成员锁内再次检查。现有连接继续处理发言、广播和回执。负载均衡器应根据就绪探针把同一个站点的新连接转到健康网关，保留已建立的 WebSocket；两台网关共享 Redis、Kafka 和 PostgreSQL。测试使用本机两台网关，部署时需为目标网关预留连接容量。

浏览器通过 `/live?migrate=1` 声明支持交接。旧网关每 100 ms 发出一批 107 通知，客户端收到后从当前站点重新建立连接。新连接收到 106 时钟消息意味着房间订阅就绪；页面再读取近期快照并暂存新连接上同时收到的事件。旧连接持续更新页面。读取快照期间若旧连接推进了游标，页面只应用缺失的后缀；若整个快照已落后则保留现有游标。交接成功后关闭旧连接并处理暂存帧，过期连接的回调不能覆盖新连接状态。新连接失败会保留可用的旧连接，带随机抖动退避重试。

默认每批最多邀请 100 人，在途最多 64 人。已邀请的旧连接释放时归还名额，因此新网关握手或补发变慢时，下一批可用名额也减少。反馈来自旧连接释放速度，没有直接采集目标机器 CPU。用户主动离开或网络断开也会释放名额。通知通过独立的单槽信号进入已有 WebSocket 写协程。

| 网关参数 | 默认值 | 含义 |
|---|---:|---|
| `-migration-batch` | 100 | 每 100 ms 的邀请上限 |
| `-migration-inflight` | 64 | 已邀请且旧连接仍存活的人数上限；0 表示只按固定速率邀请 |
| `-migration-timeout` | 30s | 整个交接阶段的截止时间；0 表示直接进入关闭流程 |

截止时间到达后，网关继续原有的关闭和队列排空流程。未声明迁移能力的客户端依靠断线重连。部署平台的终止宽限期应覆盖交接时间以及后续最多 5 秒的关闭时间。单网关本地调试可设 `-migration-timeout=0`。突发宕机时由客户端退避、游标恢复及窗口过期后的近期重置兜底。超出近期恢复窗口的观众只能恢复近期视图。

## 复现

启动独立 Redis、PostgreSQL、Kafka，将 `REDIS_ADDR`、`DATABASE_URL` 和 `KAFKA_BROKERS` 指向该环境。构建网关后，下面的工具会为每一轮启动并结束两个测试进程。每个进程应有足够的文件描述符；默认使用本机 38980、38981 端口，可通过 `-port` 调整。

```sh
export GATEWAY_BIN="$(mktemp -d)/gateway"
go build -o "$GATEWAY_BIN" ./cmd/server
for strategy in crash fixed bounded; do
  go run ./cmd/benchmark/migration -gateway "$GATEWAY_BIN" -viewers 10000 -strategy "$strategy"
done
```

Chromium 验收使用项目现有的 Playwright 测试环境，运行 `node scripts/check-migration.cjs`。通过 `GATEWAY_A_PORT`、`GATEWAY_B_PORT` 可指定两个空闲端口。浏览器用同源代理切换接入点，故意让一次补发请求返回 503，并延迟下一次快照响应。此时旧连接仍能显示新弹幕；交接结束后，页面中下线前、交接中、下线后的三条弹幕顺序正确且各出现一次。测试同时检查源网关拒绝新接入。原有 `scripts/check-recovery.cjs` 使用 SIGKILL 独立验证突发宕机后的增量补发、撤回和窗口过期重置。

## 万人实验口径

每轮两个网关各有 5,000 个轻量 WebSocket 观众，同一热房、同一访客 cookie，正式会话接口。发送端每 250 ms 发一条带序号的消息，共 80 条，第 3 条前触发 A 下线。目标 B 原有观众持续收包。每个迁移观众向 B 确认身份、建连、按游标补发，失败则带抖动重试。负载工具直接选取 B；同源入口切换另由 Chromium 验证。负载工具对每位观众核对连续序号和前驱游标，合并快照与缓冲区中的重叠后，期望每轮共 800,000 次应用层投递。

峰值按下线信号起每个整秒内启动的迁移尝试数统计，含重试。单人恢复耗时从收到邀请或检测到断线开始，到新网关的快照合并完成；它不含等待首个邀请的时间。全部迁移耗时从发下线信号开始。原有观众 P99 统计 B 原有 5,000 人从第 3 条起的每条投递，起点是网关生成消息的时间，终点是负载工具解码并核对序号。各进程同机。本实验覆盖交接阶段，业务流量 4 条/秒；更高发送速率、不同设备与公网链路需要单独测量。

## 九轮实测

每种策略三轮，表内取各轮指标的中位数。九轮均由一万名观众各自应用 80 条连续弹幕并核对前驱游标，累计 720 万次应用层投递；全部迁移人数每轮均为 5,000。[逐秒尝试数与逐轮结果](benchmarks/gateway-migration.jsonl)

| 策略 | 峰值尝试/秒 | 单人恢复 P99 | 全部迁移耗时 | B 原有观众投递 P99 |
|---|---:|---:|---:|---:|
| 突然退出，带抖动重连 | 5,013 | 1052 ms | 1.37 s | 184 ms |
| 每 100 ms 最多邀请 100 人 | 1,000 | 83 ms | 5.03 s | 179 ms |
| 同样批次，上限 64 人在途 | 640 | 95 ms | 8.01 s | 176 ms |

本机的固定速率组与在途上限组都收齐。固定速率组完成整批滚动更早；64 人上限组允许用较长的发布窗口换取较低的尝试峰值。原有观众 P99 的几毫秒差距受同机调度影响，三轮数据不足以据此推荐某个通用阈值。按容量选参还应考虑最长允许发布时间、入口摘流耗时、观众数量及目标网关余量。

早期预跑中的突发退出组只试一次建连，5,000 人中有 1,288 人因握手失败未能恢复。正式九轮加入会话确认、快照恢复和带抖动的多次重试。HTTP 压测客户端对单个目标限制最多 512 条 HTTP 连接；表内尝试数统计客户端启动迁移流程，不能直接换算成目标网关每秒成功握手数。
