# 热门房间广播、pgx 迁移与双写故障验证

本机 Apple M4，Go 1.27.3。网关、压测客户端、Redis、单节点 Kafka KRaft 和 PostgreSQL 17 都运行在专用 Compose 项目，使用同一台 4 vCPU Colima 虚拟机。每个配置运行三次并轮换顺序。CPU 时间取 Linux 网关进程的 utime + stime（100 ticks/s）；写系统调用取 /proc/PID/io 的 syscw 增量，含 WebSocket、基础设施和日志写入。客户端另计热房间的实际帧数。

## 512 位观众

每轮热房间以目标 1,000 条/s 持续发送 2 秒，预期 1,024,000 次投递。另设小房间，每秒发送 20 个探针。所有连接都读消息，按连接校验计数；热门房间的第一个连接和小房间连接分别测量从发送到收包的逐条 P99。下表为三轮中位数，最后一列为三轮合计缺失的投递次数。

| 发送方式 | 网关 CPU 秒 | 写系统调用 | 热房间帧数 | 热房间 P99 ms | 小房间 P99 ms | 缺失投递 |
|---|---:|---:|---:|---:|---:|---:|
| 逐条 | 3.20 | 1,027,595 | 1,024,000 | 30.98 | 15.06 | 1,536 |
| 逐条 + 预制帧 | 3.29 | 1,027,598 | 1,024,000 | 29.45 | 18.51 | 5,120 |
| 5 ms 合批 | 1.24 | 214,887 | 210,944 | 11.72 | 3.55 | 0 |
| 5 ms 合批 + 预制帧 | 1.41 | 215,993 | 211,968 | 11.54 | 6.89 | 0 |
| 50 ms 合批 + 预制帧 | 0.63 | 51,601 | 47,616 | 43.58 | 10.76 | 0 |

逐条基线有一轮接收量低于目标 0.15%。仅取两轮完整接收的逐条基线，其 CPU 时间为 3.16、3.20 秒，写调用为 1,027,611、1,027,595，热门房间 P99 为 30.98、24.10 ms。5 ms 合批三轮均完整接收。每轮小房间只有 40 个探针，尾延迟容易受共享主机调度影响。

## 64 位观众

保持目标速率，每轮 3 秒。每种方案的每轮都收齐热房间 192,000 次投递和小房间 60 个探针。

| 发送方式 | 网关 CPU 秒 | 写系统调用 | 热房间 P99 ms |
|---|---:|---:|---:|
| 修改前工作区版本 | 1.09 | 196,031 | 0.89 |
| 新版逐条 | 1.08 | 196,029 | 0.69 |
| 逐条 + 预制帧 | 1.15 | 195,951 | 0.93 |
| 5 ms 合批 | 1.11 | 39,595 | 7.76 |
| 5 ms 合批 + 预制帧 | 1.07 | 38,940 | 7.75 |
| 50 ms 合批 + 预制帧 | 1.10 | 12,169 | 36.13 |

两个房间规模的固定策略实验均允许合批。根据上述结果，默认仅在房间有至少 128 位支持批量协议的观众时开启 5 ms 合批。128 是位于两组实测规模之间的起始阈值，可用 `-batch-min-viewers` 调整。预制帧作为可选参数。高扇出时网关减少了写调用和 CPU 时间；较低扇出、相同高发送频率时，等待批次会增加延迟。超过 32 条或 32 KiB 提前发出。适用范围是本次单机、持续读取、短 JSON 弹幕负载。压测入口示例：

```sh
go run ./cmd/server -batch-window 5ms -prepared=false
go run ./cmd/benchmark/fanout -viewers 512 -rate 1000 -seconds 2
```

最终默认配置另做一次端到端验证。64 人房间收齐 128,000 条，使用 128,000 帧；512 人房间收齐 1,024,000 条，使用 211,456 帧；旧协议房间收齐 64,000 条，每帧一条。

## PostgreSQL 与双写

* 新旧版本均使用每批 1,000 行的 UNNEST SQL，保留唯一事件索引。每轮向各自的空表写入 50,000 个随机事件 ID，每轮核对行数。旧版三轮为 84,811、93,321、97,012 行/s，pgxpool 为 98,042、82,594、94,445 行/s。中位数差约 1.2%，小于轮间波动。
* 空库与模拟旧库均通过并发启动、版本登记、游标查询和幂等重放测试。另在测试库恢复项目现有数据库的 schema，插入一条最大 uint64 用户 ID 的旧记录，迁移后仍可读取，event_id 保留 NULL。集成测试使用 DANMAKU_TEST_DATABASE_URL，在测试库内创建独立 schema。
* 关闭 Kafka 后启动网关，向同一房间发送 17,000 条，客户端收到 17,000 条。Kafka 恢复后查询数据库得到 16,384 个不同事件 ID，队列满计数为 616。
* Kafka 健康时，临时禁止测试 Redis 用户执行 PUBLISH，12 条弹幕均未实时送达，历史库有 12 个不同事件 ID。也验证了两种故障重叠时两条链路都可能失败。解除限制后，正常测试的 12 条均送达并入库。
