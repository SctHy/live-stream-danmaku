## 连接队列与房间延迟

`go test ./internal/ws -run '^$' -bench BenchmarkConnectionAllocation -benchmem -count=3` 可比较三种队列容量。每次创建客户端的分配量分别为 3,424 B（128 条）、13,792 B（512 条）和 98,529 B（4096 条）。测试只创建客户端、channel 和相关对象；未建立 TCP 连接或测进程 RSS。

在专用测试服务上运行 `go run ./cmd/benchmark/rooms -addr 127.0.0.1:28080`。一个热门房间建立 12 个连接，其中 4 个合计以目标 4,000 条/s 发送 3 秒。同时，小房间每 10 ms 发送探针，测量发送到收到广播的时间。两版都使用同一 Redis、KRaft 和 4096 条的客户端队列，基线只调整了测试 Redis 地址。端到端路径包括 WebSocket、Kafka 输入队列、Redis 发布订阅和客户端接收。

| 轮次 | 旧版小房间 P99 | 新版小房间 P99 |
|---|---:|---:|
| 1 | 402.924 ms | 2.266 ms |
| 2 | 296.373 ms | 1.269 ms |
| 3 | 290.756 ms | 0.913 ms |

六次均在小房间收到 300 条探针，热房间观测连接收到 12,000 条。另测新版 128、512、4096 三档各一次，也均达到相同接收数；这些连接持续读取，慢观众或分片哈希碰撞可能有不同表现。默认选 512 保留一定突发余量。现有在线容量宣传值未复测。

## 历史写入与故障恢复

每轮调用真实仓储方法写入 60 批，每批 1,000 行，完成后按行数校验。旧版三次为 112,798、109,536、109,854 行/s；新版为 103,907、102,646、101,995 行/s。对照包含新版唯一索引及幂等处理；新版基准使用按序生成的短事件 ID，生产随机 ID 和更大的索引可能改变结果。此项测数据库写入，不包括 Kafka 排队或 JSON 解析。

另在相同的幂等表中，每轮测试 40 批，每批 1,000 行。三次中位数为 GORM 批量 INSERT **72,690 行/s**、pgx COPY 到临时表再合并 **92,118 行/s**、UNNEST 数组批量 INSERT **115,230 行/s**。最终采用 UNNEST，通过现有连接池执行一条带 ON CONFLICT 的语句。该实验使用独立表、驱动调用和数据集，用来比较候选方案。

故障测试向专用 Kafka 主题写入 1,000 条旧格式弹幕，通过 PostgreSQL CHECK 约束暂时拒绝写入。观察到首次失败后再等待 3 秒，解除约束并等待恢复。旧版落库 0 条；新版落库 1,000 条。用新消费组从头重放 1,000 条后，数据库仍为 1,000 行，消费组 lag 为 0。另有单元测试覆盖未确认批次在会话取消后的重放。此保证从成功进入 Kafka 的有效记录开始，Redis 发布与 Kafka 写入仍为两个独立操作。

## KRaft

原 Compose 使用 Kafka 2.8.1 和 ZooKeeper，新 Compose 使用 Apache Kafka 3.9.1 的单节点 broker/controller。提前拉取镜像，每轮使用空卷，从 compose up 开始，到宿主机 Sarama 客户端首次成功获取主题元数据为止。旧版三次 2.503、2.392、2.440 秒；新版 1.519、1.447、1.386 秒。变化包含 Kafka 版本、镜像和旧 ZooKeeper 在 arm64 主机上的 amd64 模拟开销。未单独测量 Kafka 消息吞吐。

保留命名卷并强制重建新版 broker 后，测试主题末端位点和重放消费组已提交位点均为 1,000，lag 为 0。此次测量覆盖单节点开发部署。
