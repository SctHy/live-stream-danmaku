# 优化迭代记录

| 为什么改 | 怎么改 | 验证结果 |
|---|---|---|
| 热房挤占队列，小房间也要等 | 按房间分片处理；缩小每个连接的发送队列 | 热房加压时，冷房 P99 从 296 降至 1.27 ms；单连接创建分配量下降 86%。[实测](kraft-benchmarks.md) |
| 数据库短时拒写会丢历史记录 | 消费者写入成功后再确认，按事件 ID 幂等重放 | 拒写后恢复，1,000 条全部入库；再次重放仍为 1,000 条。[实测](kraft-benchmarks.md) |
| 本地 Kafka 依赖 ZooKeeper，启动较慢 | 迁移到单节点 KRaft | 空集群元数据就绪时间从 2.44 降至 1.45 秒（含版本和镜像变化）。[实测](kraft-benchmarks.md) |
| 高频弹幕逐条写连接，热门房间开销大 | 对足够大的房间启用 5 ms 合批，小房间直接发 | 512 人、1,000 条/秒时，每轮网关写调用从 103 万降到 21.5 万，热房 P99 从 31 降到 12 ms。[实测](fanout-benchmarks.md) |
| 只看收包总数，漏一条和重复一条可以抵消 | 每位观众独立核对消息序号和游标，每台网关单独采样延迟 | 回归测试能识别总数相同的漏收和重复，并定位序号。[校验代码](../cmd/benchmark/fanout/main_test.go) |
| 万人房间每秒 50 条时，默认 2 ms 到达间隔很少触发合批 | 分开配置到达间隔和等待窗口；万人实验取 250 / 180 ms | 8 秒短测投递率中位数从 39.5% 到 100%；15 分钟收齐 4.5 亿次，两个热房探针 P99 为 286 / 293 ms。[实测](hot-room-capacity.md) |
| 单测补发和撤回，容易漏掉两者同时发生的情况 | 在观众掉线时撤回，分别验证增量补发和窗口过期重置 | 两种情况下，重连页面、近期查询和回放都隐藏了目标弹幕。[验收](hot-room-capacity.md#浏览器故障验收) |
| 旧回放层和全局路由注册增加维护成本 | 移除旧入口，HTTP 层只依赖回放与撤回接口，网关直接分派两种上行消息 | 回放只维护一套媒体时间分页逻辑；网关启动无需注册全局处理器。[HTTP 接口](../internal/api/chat_handler.go) · [消息路由](../internal/ws/router.go) |
| 回执丢失后重发可能重复，Kafka 停机时已发布弹幕可能漏存 | 正式会话按用户、场次及请求 ID 原子去重，连同待归档记录一起发布，Kafka 确认后清理 | 跨网关 12 次重试均返回原 ID，近期与恢复后的回放各一条；浏览器重连重试保留原请求。[验收](hot-room-capacity.md#发言重试与-kafka-停机验收) |
| 滚动发布时集中重连会挤占目标网关容量 | 网关先摘流、分批通知并限制在途交接；浏览器在新连接补齐游标后关闭旧连接 | 万人对照九轮均收齐，5000 人迁移的尝试峰值中位数由 5013 降至 640 次/秒，单人恢复 P99 由 1052 降至 95 ms。[实测](gateway-migration.md) |
| 协议定义分散，预编码帧分支增加复杂度 | 集中消息类型与载荷，移除预编码与未使用的建表语句 | Go 1.27.4 构建及全仓竞态单测通过。 |
| 双写路径与逐房订阅增加重复处理和连接数 | 统一会话入口、房间原子发布与网关投递，在归档端隔离坏记录 | Redis 实测 100 房间占用 8 条订阅连接，数据库迁移、坏记录与竞态测试通过。 |
| 单一管理器混合房间、广播和网络 I/O，空闲连接缺少保活 | 按成员、派发、统计与迁移拆分 Hub，挂接 Ping/Pong 和 500ms 上行时限 | 快照、慢客户端、迁移及全仓竞态测试通过。 |
| 网关和归档依赖多个框架及全局日志 | 改用 ServeMux、slog 与 franz-go，手动提交分区位点 | 四项直接依赖；独立 Compose 双网关跨节点广播、重连、去重回放、禁言撤回与竞态测试通过。 |
