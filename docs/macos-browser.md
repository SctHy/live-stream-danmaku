# macOS 和 Ardia 的直播弹幕

## 本机运行

在仓库根目录运行：

```sh
./scripts/dev-mac.sh --open
```

脚本使用 Go 构建网关和归档消费者，前台运行两个原生进程。需要 Go、Docker Compose 和已运行的容器引擎。脚本优先复用已有项目的 Docker context，读取 Compose 实际映射的端口。没有项目容器时使用当前 Docker 引擎创建服务，本机 Redis 的默认映射为 26379。可用 `DOCKER_CONTEXT`、`COMPOSE_PROJECT_NAME` 和 `PORT` 指定环境。按 Ctrl-C 停止此次启动的 Go 进程。已有容器和数据卷可供下次使用。

默认入口是 `http://127.0.0.1:8080/`。加 `--open` 会调用 Ardia CLI，没有该命令时使用 macOS 默认浏览器。页面、脚本与 30 秒示例 MP4 均随 Go 二进制嵌入。本机验证使用 Apple Silicon、Go 1.27.4 和 Colima 的 aarch64 虚拟机。

房间和场次由 URL 的 `room`、`session` 指定，各允许 1–24 个 ASCII 字母、数字、下划线或短横线。每场直播使用独立的场次标识。Demo 循环播放同一段视频，按网关时钟对齐画面；在第几秒发送，就在回放的第几秒出现。接入真实播放器时由播放器提供媒体时间。没有媒体时间的旧记录仍在历史库中。

在“本地样本”中同时选择视频和弹幕 JSON 即可测试自己的片段。JSON 使用数组格式，例如 `[{"video_offset_ms":1250,"content":"第一条弹幕"}]`。弹幕时间以视频起点为零，单位为毫秒。浏览器在本机读取这两个文件。点击“直播”或“回放”可返回房间。

## 会话与投递

浏览器先 `POST /api/session` 领取 24 小时的 HttpOnly、SameSite=Strict 访客 cookie，再连接 `/api/rooms/{room}/{session}/live`。WebSocket 使用同源握手并支持 `danmaku.batch.v1`。原命令行的 `/ws?uid=…&room=…` 使用独立房间，仅向直接连接回环地址的非浏览器客户端开放。反向代理对外发布时只转发浏览器入口和静态资源。

| 消息类型 | 用途 |
| --- | --- |
| 101 | 发弹幕可带 `client_msg_id` 和 `video_offset_ms`，下行带服务端生成的 `event_id` |
| 102、103 | 房间统计快照、点赞。单次点赞 1–20 |
| 104 | 发送回执，带原 `client_msg_id`；成功时带原 `event_id`。可返回 `accepted`、`invalid`、`overloaded`、`muted`、`rate_limited` 或 `unavailable` |
| 105 | 按 `event_id` 撤回弹幕 |
| 106 | 房间订阅就绪，含服务器时间 |

`accepted` 表示事件已进入网关发布队列。队列拥堵时最多等 25 ms。Redis 直播发布与 Kafka 历史写入仍可分别失败。回执用于关联这次发送，客户端重发会产生新的事件。匿名访客更换浏览器身份后会获得新的用户 ID。

Redis 在一次脚本调用中追加房间 Stream 并发布事件。每场保留最近 256 个事件，空闲 120 秒过期。`pos` 含本次 Stream 的随机标识和 Redis 位点，`prev` 指向上一条。重连后客户端先等 106，再拉 `GET …/recent?after=<pos>`，期间缓存新到的直播帧。游标失效时服务端返回 `reset=true` 和当前窗口。统计快照还携带最新位点，最后一条直播消息丢失时也能触发补发。

`GET …/playback?from=0&until=10000&after=0` 读取左闭右开的媒体毫秒区间，每页至多 100 条。下一页带上一页末条的 `video_offset_ms` 和数据库 `id` 作为 `from` 与 `after`。历史由消费者异步写入，刚发送的消息可能稍后才进入回放。

## 房管与运行状态

网关可设置 `DANMAKU_MOD_ROOM` 和 `DANMAKU_MOD_TOKEN`。同一房间的多个网关使用相同配置。房管在页面展开“房管操作”，输入密钥并选择目标消息，即可撤回或将这名访客禁言 60 秒。密钥只在当前页面使用。对应的 `POST …/moderate` 使用 Bearer 验证，禁言支持 1–86400 秒。每个访客在每场每秒最多发 8 条弹幕或 8 次点赞，两类动作分别计数。

撤回先记录 PostgreSQL 删除标记，即使原消息随后才入库，回放查询也会隐藏它。撤回事件会更新在线客户端和重连窗口。若实时通知失败，接口返回 503，同一撤回可重试。持续慢读的连接达到 8 次连续帧入队失败后会被关闭。在线人数和点赞只保留最新的待发快照。

`/livez` 检查进程，`/readyz` 检查 Redis 和 PostgreSQL，滚动摘流期间返回 503。浏览器的 107 迁移通知及部署参数见[网关滚动下线](gateway-migration.md)。`/metrics` 返回 JSON，包含分片丢弃、单连接丢弃、发布队列拒绝、队列等待总时长、实时日志错误及历史队列长度。浏览器发言的待归档量用 Redis 命令 `XLEN dm:archive:pending` 查看，并结合 Kafka 消费组 lag 排查。当前页面在首次发送后 9 分钟内可用原请求重试，服务端去重保留 10 分钟。刷新页面会清除本地待确认请求。

## 本机验收

在独立 Compose 项目中运行 PostgreSQL 17、Redis 7.4、Kafka KRaft，以及两个原生 Go 网关和一个消费者。用两个 Ardia 标签页连接同一场次的不同网关。第二个网关退出期间，第一个网关发送两条弹幕，第二个重启后原页面自动补齐，列表中三条消息各出现一次。回放定位到 12.95 秒后，13.124 秒的弹幕按时出现。房管撤回后，直播窗口、近期查询和历史查询均隐藏了该条消息。被禁言的访客收到了拒绝回执。一次独立探针从开始握手到收到广播耗时 15 ms，到 HTTP 查询可见耗时 1.83 秒，查询轮询间隔 100 ms。

### 双网关压测

两个网关均使用 `-room-shards 1` 强制热房和冷房争用同一分片。384 个持续读取的热房观众交替连接两台网关，每八人有一人使用逐条协议，另接入 8 个停止读取的观众和 64 个空闲房间。每 100 ms 做一次热房加入和离开。每轮向热房发 300 条/秒，持续 8 秒，运行三轮。以下 P99 是三轮各自 P99 的中位数。

| 路径 | 正常热房观众每轮收包 | 热房 P99 | 冷房 P99 | 两个网关各自的最高采样 RSS |
| --- | ---: | ---: | ---: | --- |
| 浏览器访客会话 + Redis 恢复窗口 | 921,600 / 921,600 | 13.78 ms | 9.37 ms | 43.0 / 55.4 MiB |
| 本机 CLI 路径 | 921,600 / 921,600 | 10.53 ms | 7.98 ms | 45.7 / 53.0 MiB |

浏览器协议压测使用 Go WebSocket 客户端，并分摊发送到不同访客。冷房每轮只有 40 个样本，其首轮 P99 为 45.93 ms。CLI 路径每轮有 160 个冷房样本。RSS 每 250 ms 用 macOS 的 `ps` 采样，包含进程基线。以上数据描述本机短时负载。停止读取的连接不计入正常观众收包率，浏览器协议三轮均未触发应用层队列丢弃。

```sh
go run ./cmd/benchmark/fanout -browser \
  -addr 127.0.0.1:8080 -peer 127.0.0.1:8082 \
  -viewers 384 -legacy-every 8 -stalled 8 -idle-rooms 64 \
  -churn 100ms -rate 300 -seconds 8
```

### Redis Streams 单独承担归档的实验

另用本机 Redis 8.10.3 的独立实例验证积压和恢复。启用 AOF、每秒 fsync，写入 17,000 个带随机事件 ID 的短消息，消费者暂停时 Stream 键占用 3,293,892 字节。等待两秒后强制终止并重启该测试进程，17,000 条仍可读。每批 500 条通过现有仓储写入 PostgreSQL，将首批重复写入以模拟提交后丢失确认，最终有 17,000 条唯一记录，消费组 pending 为零。此次本机清空积压用时约 0.45 秒。

实验覆盖单机、短积压和已经完成一次 fsync 的情况。替换归档路径还需明确最长停写时间及对应的内存和持久性预算。本版使用有界 Stream 提供短时恢复，继续使用已有 Kafka 承接长期归档积压。
