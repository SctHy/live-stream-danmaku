# 千人和万人热门房间的端到端实验

工作负载采用每个房间总计每秒 10、25、50 条短弹幕，观众通过持续读取的 WebSocket 连接接收。10,000 人 × 50 条/秒意味着每秒 500,000 次逻辑投递。每一条消息可以出现在多个连接的帧中，一个帧也可能含多条消息。本实验独立统计上行条数、热房有效投递和数据帧数。

## 万人 15 分钟验收

双网关各接入 5,000 个批量协议访客；180 ms 窗口、250 ms 到达间隔上限。单次持续 900 秒，实际发送速率 50.00 条/秒，45,000 条弹幕分别送到所有 10,000 名观众。**4.5 亿次期望投递全部收齐，每位观众缺失、重复、游标断点均为零。** 两个热房探针各记录 45,000 个样本，P50 分别为 155 和 163 ms，P99 分别为 286 和 293 ms。冷房探针收到 4,500 / 4,500 条，P99 为 64 ms。

热房客户端共收到 40,755,000 个含弹幕的数据帧，平均每帧约 11 条，应用数据共 155.9 GB。两个网关合计使用 575.23 CPU 秒，合计峰值 RSS 约 600 MiB；压测端峰值 RSS 约 480 MiB。两端网关的发布拒绝、应用投递丢弃、日志错误最终计数均为零。每 30 秒的内存和队列采样已随原始结果保存。这一结论覆盖本机回环、两个网关、短消息和持续读消息的访客；公网抖动以及万人混合旧协议的容量需单独测量。

## 测量方法

在 Apple M4（10 核、16 GiB、macOS）上运行原生 Go 1.27.4 网关、消费者和压测器。独立 Compose 项目的 Redis 7.4、Kafka 3.9.1、PostgreSQL 17 使用同机 4 vCPU、6 GiB 的 Colima 实例。增加网关数量时共用同一台机器。访客走正式的会话、限频、Redis 房间日志和 WebSocket 路径。压测器完成所有订阅握手后才开始发送，每个网关各采一位热房观众，另有一个每秒 5 条的冷房探针。

- 每轮使用独立房间。每个读者用位图核对本房间的消息序号，检查重复、缺失和服务端游标的前后关系。任一正常观众验证失败，工具返回非零状态。断开的测试连接不做在线补发，以便暴露实时交付缺口。
- 延迟从客户端写入前的时间戳算到读取 WebSocket 帧，包含本机调度。按网关列 P50/P99 和样本数；8 秒冷房只有 40 个样本。丢包轮次的延迟只代表成功收到的消息。
- 网关 CPU 时间覆盖建连、发送、排空和断连，RSS 为每 0.5 秒采样的进程常驻内存。客户端记录的是含弹幕的 WebSocket 应用数据字节，不含 TCP、WebSocket 头和统计帧。吞吐测试使用 Go 访客，不包含浏览器上屏时间。容量验收以实时投递为准，未逐条核对这些负载消息的 Kafka 归档。
- 合批有三个条件：接入网关上的批量协议观众数、相邻消息的到达间隔和合批窗口。默认分别为 128 人、2 ms 和 5 ms。第一条立即发送；逐条协议客户端一直单发。可通过 `-batch-min-viewers`、`-batch-arrival-gap`、`-batch-window` 单独调整。房间有一万人也可能每帧只有一条弹幕。

[逐轮原始结果](benchmarks/hot-room.jsonl)含网关参数、校验结果、样本数和资源采样。最初的连续建连预跑耗尽了 macOS 压测端临时端口，部分配置在握手阶段失败。压测器随后在读数完成后以 TCP reset 释放测试连接，无需调整主机网络参数。握手失败记录保留在 preflight 组，未计入投递率。

## 短时容量与参数选择

每组发送 8 秒，最多再等 10 秒排空。下表为三轮中位数，P99 先取各热房网关探针中的最大值。通过要求冷热房都收齐，且无重复或游标断点。测试机同时承担发送、网关和接收校验负载，限流拒绝的消息也计入期望投递分母。

| 观众 / 网关 | 房间条数/s | 合批窗口 / 到达间隔上限 | 通过轮数 | 热房投递率 | 热房探针 P99 | 冷房探针 P99 |
|---|---:|---|---:|---:|---:|---:|
| 1,000 / 1 | 50 | 5 / 2 ms | 3/3 | 100% | 10.8 ms | 14.7 ms |
| 1,000 / 2 | 50 | 5 / 2 ms | 3/3 | 100% | 10.9 ms | 8.9 ms |
| 1,000 / 4 | 50 | 5 / 2 ms | 3/3 | 100% | 10.8 ms | 20.0 ms |
| 1,000 / 8 | 50 | 5 / 2 ms | 3/3 | 100% | 9.6 ms | 14.0 ms |
| 10,000 / 2 | 10 | 5 / 2 ms | 3/3 | 100% | 258 ms | 75 ms |
| 10,000 / 2 | 25 | 5 / 2 ms | 0/3 | 76.50% | 7,604 ms | 1,572 ms |
| 10,000 / 2 | 25 | 45 / 48 ms | 1/3 | 94.95% | 6,239 ms | 1,577 ms |
| 10,000 / 2 | 50 | 5 / 2 ms | 0/3 | 39.50% | 8,213 ms | 1,461 ms |
| 10,000 / 2 | 50 | 45 / 48 ms | 0/3 | 50.75% | 6,496 ms | 1,259 ms |
| 10,000 / 2 | 50 | 180 / 250 ms | 3/3 | 100% | 335 ms | 84 ms |

千人、50 条/秒时，四种拓扑均是每轮 40 万帧。8 网关的本地 125 人低于合批门槛，但另三组即使人数足够，正常到达间隔 20 ms 也超过默认的 2 ms。增加本机网关数量后，网关合计峰值 RSS 中位数从约 66 MiB 增至 267 MiB。另做了千人每秒 10 条（单网关）和 25 条（双网关）的 10 秒预跑，分别完整投递 10 万和 25 万次。

万人、50 条/秒时，单轮期望 400 万次投递，180/250 ms 配置的实收帧数中位数为 36 万，网关 CPU 中位数为 8.26 秒，约每万次有效投递 0.021 CPU 秒。本机默认配置会出现发布队列拒绝；例如一轮两台网关合计拒绝了 242 条上行，恰好对应 242 万次缺失投递。排队延时和未收齐率表明这一档已经过载。机器共享和调度也会影响 Redis 往返、压测器解码和内核网络，以上观测不足以把过载全部归因于其中一个组件。

额外把 180 ms 窗口的到达间隔门槛收紧至 60 ms，各档各跑一次。10 和 25 条/秒均收齐，50 条/秒只收齐 397 万 / 400 万次热房投递，冷房收齐 34 / 40 条。相同窗口下，到达间隔门槛也会影响实际聚合。

第一条稀疏消息会立即发送；开启较宽窗口后，连续消息可额外等待最多一个配置窗口（调度延迟另计）。保留低延迟默认值，把宽窗口作为可配置的万人高扇出取舍。若部署中有大量小房间，可用本地批量协议观众数限制适用范围。旧协议观众逐条接收；本次万人数据只覆盖支持批量协议的客户端。

## 复现

从仓库根目录运行。以下端口供独立实验使用；在共享机器上为环境选择空闲端口。使用非默认 Docker context 时先导出对应的 `DOCKER_CONTEXT`。

```sh
export COMPOSE_PROJECT_NAME=danmaku-hotlab
export REDIS_PORT=38479 POSTGRES_PORT=38432 KAFKA_PORT=38492
export REDIS_ADDR=127.0.0.1:38479 KAFKA_BROKERS=127.0.0.1:38492
export DATABASE_URL='postgres://danmaku:danmaku@127.0.0.1:38432/danmaku_db?sslmode=disable'
docker compose up -d
# 等 Kafka、Redis 和 PostgreSQL 就绪，另开终端用同一环境运行消费者。
go run ./cmd/consumer
```

压测脚本构建二进制，为每一轮新建网关，分配观众，输出 JSON 行后关闭本轮进程。可将 stdout 重定向到文件保存失败轮次。每个网关和压测进程均需要足够的文件描述符。一万人的客户端至少需要一万个可用套接字。

```sh
python3 scripts/hot-room-bench.py --viewers 1000 --gateways 2 --rate 50 --seconds 8 --rounds 3
python3 scripts/hot-room-bench.py --viewers 10000 --rate 50 --seconds 8 --rounds 3 --policies 5ms/2ms,45ms/48ms,180ms/250ms
python3 scripts/hot-room-bench.py --viewers 10000 --rate 50 --seconds 900 --policies 180ms/250ms
```

若要在应用入口复现万人配置，在共享同一组 Redis、Kafka、PostgreSQL 的两个终端分别运行以下网关，并将一万名支持批量协议的观众均分到两端。普通启动仍采用 5/2 ms。

```sh
go run ./cmd/server -port 8080 -batch-window 180ms -batch-arrival-gap 250ms
go run ./cmd/server -port 8082 -batch-window 180ms -batch-arrival-gap 250ms
```

## 浏览器故障验收

使用独立环境中的两个网关、一个消费者和真实 Chromium。测试从同一场次的两个页面观察弹幕，确认目标已在回放入库，再停止测试拥有的网关 A，在 B 上撤回，并分两次开放观众到 B 的连接。短暂断线验证增量恢复；另一个观众等 260 条新消息裁掉旧游标后重连，验证重置后整个侧栏的顺序、内容和数量，同时查询近期接口和原媒体毫秒对应的历史分页。

在上面的环境中导出同一个 `DANMAKU_MOD_ROOM`、`DANMAKU_MOD_TOKEN`，用该配置启动网关 B。脚本只结束自己启动的 A。需要 Node.js、Playwright 和它的 Chromium；也可以用 `NODE_PATH` 指向已有的测试依赖，用 `CHROMIUM_PATH` 指向已有的浏览器可执行文件。

```sh
export DANMAKU_MOD_ROOM=recovery
export DANMAKU_MOD_TOKEN=local-test-only
export GATEWAY_BIN="$(mktemp -d)/gateway"
go build -o "$GATEWAY_BIN" ./cmd/server
"$GATEWAY_BIN" -port 38502 & b_pid=$!
node scripts/check-recovery.cjs
kill "$b_pid"
```

本机浏览器验收中，两页均先看见目标弹幕，撤回前的回放查询也能读到它。恢复窗口内，页面补到一条保留消息，开放到 B 后 395 ms 完成校验；窗口外，页面重置为最新 100 条，顺序逐条一致，3,486 ms 完成校验。两次均验证近期响应和历史回放隐藏了目标消息。这些是单次受重连退避影响的结果。

## 发言重试与 Kafka 停机验收

使用独立的 Redis、Kafka、PostgreSQL、两个网关和一个消费者。停止 Kafka 后，通过正式会话入口在 A 发言，由近期接口独立确认发布，发送连接关闭且不读取回执。使用相同访客 cookie，通过 B 的 12 个连接重发相同请求。12 个成功回执均返回首次发布的事件 ID，近期查询只有一条。Kafka 停机时 Redis 待转发量为 1，恢复后归零，原媒体时间段回放只有一条且 ID 一致。独立 Chromium 测试在首个发送请求到达网关前断开连接，页面重连后点击重试，浏览器两次发出的请求 ID、文本及媒体时间完全一致，最终显示该消息。

复现后端验收时，让两个网关和消费者共享独立测试环境。停止该环境的 Kafka，设置两个网关地址并运行以下测试。看到等待归档日志后，在两分钟内恢复 Kafka。

```sh
DANMAKU_TEST_GATEWAY_A=http://127.0.0.1:38680 \
DANMAKU_TEST_GATEWAY_B=http://127.0.0.1:38681 \
go test -count=1 -v -run TestRetryAcrossGateways ./cmd/server
```

去重窗口为 10 分钟。待归档流独立于近期窗口，在 Kafka 确认前保留；重复转发由数据库事件 ID 唯一约束处理。该实验覆盖 Kafka 故障，Redis 数据丢失超出验证范围。
